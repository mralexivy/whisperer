# Wispr Flow — Competitive Teardown

**Subject:** Wispr Flow for macOS, version **1.6.675** (build commit `cb6ed0ebcb7ba622aede983514498e9e89d3a8b0`)
**Analysis date:** 2026-08-29
**Method:** static analysis of the installed application bundle, the extracted `app.asar`, the local SQLite database, on-disk config and feature-flag state, and application logs. No network requests were issued, no traffic was intercepted, and no authentication was attempted. All artifacts were read from a copy; originals were untouched.
**Vendor:** Wispr AI INC, Apple Developer ID team `C9VQZ78H85`.

---

## 1. Executive summary

Wispr Flow is an **Electron application with a native Swift accessibility helper**. It performs **zero on-device machine learning**. Every inference step — speech recognition, text formatting, tone detection, polish, command routing, OCR — is a network call to Wispr's backend. If the network is down, the product produces no text at all.

The architecture is best understood as three concentric layers:

1. **A thin native layer** — a Swift helper (`LSUIElement`, no UI) that reads the focused text field via the macOS Accessibility API and injects text back into it.
2. **An Electron orchestration layer** — audio capture, context assembly, request serialization, paste-time rule-based formatting, local SQLite persistence, and a post-paste observation loop that mines the user's corrections.
3. **A cloud inference layer** — a gRPC streaming ASR service running a *multi-engine ensemble*, plus a fleet of task-specific LLM endpoints from at least four vendors.

The three findings that matter most competitively:

- **Their ASR backend is an ensemble.** The protobuf schema exposes an `Origin` enum with `WHISPER`, `SCRIBE`, `VOXTRAL`, `QWEN`, and `MIXTURE`, attached to a repeated `candidate_beams` field carrying per-beam scores, confidences, and word alignments. They run multiple recognizers in parallel and fuse the hypotheses server-side.
- **Their formatter is a fine-tuned model, not a prompt.** The only formatting model named in the client is an OpenPipe fine-tune of Llama-3.1-8B. There is no filler-word list, no punctuation regex table, no spoken-command map anywhere in the client. The formatting behaviour lives in weights.
- **They harvest an enormous amount of context and correction signal.** Every dictation ships an Accessibility dump of the focused window, the text before/selected/after the caret, the user's full custom dictionary, and their name. After pasting, a 60-second observation window watches the field and diffs what the user corrects — feeding an auto-learned dictionary.

Their median end-to-end latency is **~600 ms** from key release to pasted text, of which roughly 190 ms is network and 235 ms is GPU queue wait.

## 3. On-device inference: definitively none

This was tested exhaustively because it is the single most important architectural question.

**No model files exist, bundled or downloaded.** A sweep of the entire 582 MB bundle for `*.mlmodelc`, `*.mlmodel`, `*.mlpackage`, `*.onnx`, `*.ort`, `*.gguf`, `*.ggml`, `*.pt`, `*.safetensors`, `*.tflite`, `*.espresso.*`, `*tokenizer*`, `*vocab*`, `*.bin` returns exactly one hit: `Electron Framework.framework/.../v8_context_snapshot.arm64.bin`, which is Chromium's V8 snapshot.

The runtime directory (`~/Library/Application Support/Wispr Flow/`, 885 MB) contains no models either — it is `flow.sqlite` (346 MB), a nightly backup (345 MB), and `meetings/` (177 MB of raw PCM and Opus).

**No ML runtime is linked.**

- `otool -L` on the Electron main binary: Electron Framework + libSystem only.
- `otool -L` on the Swift helper: AppKit, Carbon, ApplicationServices, CoreAudio, CoreBluetooth, CoreData, CryptoKit, WebKit, Combine. **No CoreML, no Speech.framework, no Accelerate, no MLCompute, no MetalPerformanceShaders.**
- A full-bundle Mach-O sweep for `CoreML|Speech.framework|MLCompute|Accelerate|MetalPerformanceShaders|onnx|Espresso` returns exactly one file: the Electron Framework, which links CoreML and Accelerate because **upstream Chromium always does** (Shape Detection API, vDSP). There is no model file for it to load.
- `strings` on the Swift helper (56,307 strings) grepped for `coreml|mlmodel|espresso|ANE|SFSpeech|requiresOnDeviceRecognition|whisper|ggml|onnx|silero|vad|webrtc|MLCompute|BNNS|MPSGraph|tensor` → **zero matches**.

**Native modules are non-ML.** Three `.node` files total: `node_sqlite3.node` (2 MB, links only libc++/libSystem) and two 89-byte webpack stubs pointing at Windows `crypt32-*.node`. Plus a Jabra headset SDK. The only WebAssembly in the app is `opusscript_native_wasm.wasm` — an Opus *encoder*.

**No inference library in dependencies.** `package.json` has no `onnxruntime-node`, `@xenova/transformers`, `node-llama-cpp`, `@tensorflow/*`, or equivalent. It has `@grpc/grpc-js`, `@protobuf-ts/*`, `opusscript`, and `fft.js` (waveform visualization only).

**The word "whisper" in the bundle is a false positive.** 414 hits, all UI copy for "Whisper Mode" — a feature for dictating in a quiet voice (`whisper_education_title_private`, `whisper_demo_cta`, `usedWhisperMode`). Not OpenAI Whisper.

**"Offline" in the bundle always means network-offline buffering**, never local inference: an `[Offline Store]` envelope queue with `maxAgeDays: 30`, `meetingStartedOffline`, `offline_gap` transcript markers, `offlineRetryIntent`, `"Skipping history upload due to offline state"`, and the UI string *"You're offline. Don't worry, we're still recording"*. The `record_meeting_offline` action **records and defers**; it does not transcribe.

**No local/offline flag exists** among the 319 runtime feature flags. The nearest neighbours — `edge-proxy`, `grpc-geo`, `opus-eu-asia-experiment-v2` — are all about *which cloud region*, not local execution.

The only loopback endpoints are developer-only and gated on `!app.isPackaged`: `http://127.0.0.1:8000` (local backend) and `ws://127.0.0.1:8300/` (local dictation server).

**Verdict: raw microphone audio leaves the machine on every dictation. There is no degraded local path.**

## 4. Models

### 4.1 Speech recognition — a server-side multi-engine ensemble

The client never names an ASR model. But the compiled protobuf schema leaks the server's engine roster. From `main/index.js`, the `flow_api.v1.Origin` enum:

```js
let ot = function(e) {
  return e[e.UNSPECIFIED = 0] = "UNSPECIFIED",
         e[e.MIXTURE     = 1] = "MIXTURE",
         e[e.WHISPER     = 2] = "WHISPER",
         e[e.SCRIBE      = 3] = "SCRIBE",
         e[e.VOXTRAL     = 4] = "VOXTRAL",
         e[e.QWEN        = 5] = "QWEN", e
}({});
```

This is field 4 of `flow_api.v1.CandidateBeam`:

```protobuf
message CandidateBeam {
  Text                  text            = 1;
  float                 score           = 2;
  Confidence            confidence      = 3;
  Origin                origin          = 4;
  optional float        alignment_score = 5;
  optional string       original_text   = 6;
  repeated WordAlignment word_alignments = 7;
}
message WordAlignment { string word = 1; float score = 2; }
```

and `State.candidate_beams` is a **repeated** field. So the backend produces an N-best list where each hypothesis is tagged with the engine that generated it, carries a score and a confidence class, and has per-word alignment scores. `MIXTURE` is a fused hypothesis. This is a ROVER-style multi-engine combination.

The engines identified:

| Origin | Almost certainly |
|---|---|
| `WHISPER` | OpenAI Whisper (or a derivative) |
| `SCRIBE` | ElevenLabs Scribe |
| `VOXTRAL` | Mistral Voxtral |
| `QWEN` | Qwen audio/ASR family |
| `MIXTURE` | server-side fusion of the above |

Corroborating evidence:

- `flow_api.v1.Metadata` field 9 is `always_wait_scribe` (bool) — a per-request switch to block on the Scribe engine rather than take the fastest result. The desktop client hardcodes it off (`alwaysWaitScribe: !1`).
- `flow_api.v1.ResponseTime` has dedicated `external_asr_time` and `external_llm_time` fields, confirming the server fans out to third-party vendors.
- `Result.transcript_origin` is validated `in: ["", "internal", "external", "internal_experimental"]` — "internal" is Wispr's own model, "external" is a vendor API. In the local database, 1333 dictations are `internal`, 41 `internal_experimental`, and only 2 `external`.

**Important caveat, stated plainly:** the client decodes `candidate_beams` and discards them. The enum proves what the pipeline is *built* to return; it does not prove which engine served any given request. Determining per-request routing would require traffic capture, which was not performed.

**This user's A/B assignment** (from `feature-flags.json`):

```json

  "variant": "qwen",
  "payload": { "url": "model-qjdrgxpq.grpc.api.baseten.co|wispr-ai-abtest--abtest-qwen-flowgrpcserver.us-east.modal.direct" }
}
```

The Modal service name `abtest-qwen-flowgrpcserver` is unusually explicit. A meta-flag `dictation-ab-expt` holds `{"feature_flag_key": "dictation-ab-august13"}` — an indirection pointer so they can rotate experiments without shipping a build. Prior concluded experiments: `dictation-ab-july28`, `dictation-ab-june29`. Cadence is roughly monthly.

**Non-streaming fallback ASR is explicitly OpenAI:**

It appears only in the cloud-sync/notetaker upload classifier, not the dictation stream, and no Soniox endpoint or credential exists in the bundle.

### 4.2 Text formatting — an OpenPipe fine-tune of Llama-3.1-8B

The single most important finding for anyone building a competing formatter. `AriaWebClient.formatEnglish`:

```js
static async formatEnglish(e, t) {
  const n = (e => e === f.uC.Email
        ? "openpipe:llama3-1-05-21-data-email"
        : "openpipe:llama3-1-8b-12-09-2024")(e),
      r = { model_name: n, content: t },
      i = await Y.request("post", "/llm/formatting", r);
  return i.data ? i.data.content : ""
}
```

**Two OpenPipe fine-tunes of Llama-3.1-8B** — one general (`12-09-2024`), one email-specific (`05-21-data-email`). The request carries only `model_name` and `content`. No system prompt, no temperature, no max_tokens. **The formatting behaviour is baked into the weights.**

`formatEnglish` is defined but never called anywhere in the shipped bundle — the English client-side fallback formatter has been retired. Only the non-English fallback is live:

```js
static async formatNonEnglish(e, t, n, r) {
  const i = { app_type: e, content: t, detected_language: n, user_languages: r },
        s = await Y.request("post", "/llm/format_non_english", i);
  return s.data ? s.data.content : ""
}
```

Again, no prompt.

The **primary** formatting path is not either of these — it is the `FORMAT` step of the server-side gRPC pipeline (see §5). Its prompt, if it has one at all, is not in the client and never was.

### 4.3 The LLM fleet

Wispr uses at least **five model vendors**. Model selection is entirely server-controlled via PostHog flag payloads; nothing is configurable client-side.

**Polish / rewrite** — `polish-provider`, variant `fast`:

```json
{ "provider": { "kind": "race", "deadline_seconds": 0, "providers": [
    { "provider": { "kind": "openai",   "model": "gpt-5-nano"   } },
    { "provider": { "kind": "cerebras", "model": "gpt-oss-120b" } } ] } }
```

A **first-to-respond race** between OpenAI `gpt-5-nano` and Cerebras-hosted `gpt-oss-120b`, with `deadline_seconds: 0` meaning no deadline — pure race, whichever returns first wins. Buying Cerebras wafer-scale inference specifically for latency is a notable choice.

**Command / instruct mode** — `instruct-models`, variant `v2`:

```json
{ "classifier": "gpt-5.5", "instruct": "gpt-oss-120b",
  "modelIsUnsure": "gpt-oss-120b", "settingsUpdates": "gpt-oss-120b" }
```

The **in-bundle defaults differ from the live flag payload**, which is informative about their direction of travel:

```js
const o = { classifier:      i.nX.GPT5_5,                        // gpt-5.5
            instruct:        i.nX.Haiku,                         // claude-haiku-4-5
            modelIsUnsure:   "google/gemini-3.5-flash",
            settingsUpdates: "google/gemini-3-flash-preview" };
```

with `client_type: "OPENROUTER"` on the `modelIsUnsure` completion. So the shipped defaults route through **OpenRouter to Anthropic and Google**, while the live flag overrides everything to Cerebras `gpt-oss-120b`. The full eligible-model enum:

```js

```

**Realtime voice actions** — `wss://api.wisprflow.ai/api/v1/voice-actions/realtime`, provider hardcoded when parsing the ready frame:

```js
case "session.ready": return "string" == typeof n.model
  ? { type: "session.ready", provider: "openai", model: n.model } : null;
```

Model is **`gpt-realtime-2`**.

**Meeting pre-read agent** — `preread-config`:

```json
{ "enabled": false, "generate_for_internal_meetings": false,
  "cma_agent_model": "claude-sonnet-5", "cma_reasoning_effort": "low",
  "cma_agent_iterations": 1 }
```

`claude-sonnet-5` at low reasoning effort, one iteration. Currently gated off.

**Proper-noun extraction** — `POST /llm/extract_asr_words` is documented in their own dev tooling as **GPT-4o-mini**.

**Link labelling** — `google/gemini-3-flash-preview`.

Summary of the vendor surface: **OpenAI** (ASR fallback, gpt-5-nano, gpt-5.5, gpt-realtime-2, gpt-4o-mini), **Cerebras** (gpt-oss-120b), **Anthropic** (claude-haiku-4-5, claude-sonnet-4-5, claude-opus-4-6, claude-sonnet-5), **Google via OpenRouter** (gemini-3-flash-preview, gemini-3.5-flash), **OpenPipe** (Llama-3.1-8B fine-tunes), plus the ASR ensemble's ElevenLabs and Mistral components.

## 5. The dictation pipeline, end to end

### 5.1 The pipeline contract

The client sends a **declarative step list**; the server owns the implementation.

```js
static pipelineSteps(e = !1) {
  const t = e && (y.ZZ.status === p._W.Listening || y.ZZ.status === p._W.Stopping),
        n = (0, E.D)(),
        r = [l.LT.TRANSCRIBE, l.LT.ALIGN];
  return !(t || n === u.$Q.Raw) && r.push(l.LT.FORMAT),
         n === u.$Q.OnlyCapitalizeProperNouns && r.push(l.LT.LOWERCASE_SENTENCES),
         s().info(`Pipeline steps: ${r.join(", ")}`), r
}
```

```js
let a = function(e) {
  return e.TRANSCRIBE          = "transcribe",
         e.ALIGN               = "align",
         e.FORMAT              = "format",
         e.LOWERCASE_SENTENCES = "lowercase_sentences",
         e.SLACK_TAGGING       = "slack_tagging",
         e.EMAIL_SIGNATURE     = "email_signature", e
}({});
```

The log line `Pipeline steps: transcribe, align, format` appears verbatim in production logs. `SLACK_TAGGING` and `EMAIL_SIGNATURE` exist in the enum but no client code pushes them into the array — likely server-inferred from `app.type`.

**Crucially: while the user is still speaking, `FORMAT` is omitted.** The `t` guard checks for `Listening`/`Stopping` status. Every mid-dictation chunk is transcribe+align only; formatting is added on the final pass. This is a deliberate two-stage design.

## 6. Before / after: what the polish step actually does

Measured empirically against **1,756 real dictations** in the local database, comparing `asrText` (raw) to `formattedText` (what gets pasted).

- **83% of rows differ** (1382 / 1670 non-null pairs)
- Mean length change: **−4.3 chars** (198.8 → 194.6). The formatter **restructures; it does not summarize.**
- 103 rows have `\n` in the output; **0 rows have `\n` in the input**
- 33 rows contain `<ul>`, 17 contain `<ol>`; 0 in input
- 5 rows contain backticks; 0 in input

### 6.1 Filler removal is lexical, not acoustic

| Token | rows containing it in ASR | rows where FMT dropped it | rate |
|---|---|---|---|
| `like` | 675 | **349** | 52% |
| `basically` | 284 | **165** | 58% |
| sentence-initial `So ` | 33 | 9 | 27% |
| `uh` | 5 | 5 | 100% |
| `um` | 2 | 2 | 100% |
| `you know` | 5 | 1 | 20% |

**Only 7 rows out of 1,670 contain `um` or `uh` at all.** This is the most actionable finding in the entire teardown: **their ASR is already disfluency-suppressing at the acoustic level.** The LLM formatter's filler job is confined to *lexical* hedges (`like`, `basically`) that a faithful transcriber would correctly emit as words. They are not relying on the LLM to clean up ASR verbatimness — the recognizer itself is tuned to drop non-lexical disfluency.

### 6.2 Categories, with real examples

**A. Sentence segmentation and terminal punctuation** — present in essentially every diff. The ASR emits run-ons; the formatter splits and terminates.

> **ASR:** `I noticed something weird That the scattered row that is rendered, it's not the link I shared We're rendering something generic, we should render like real diagrams that we're pasting`
> **FMT:** `I noticed something weird: the scattered row that is rendered is not the link I shared. We're rendering something generic. We should render real diagrams that we're pasting.`

> **ASR:** `Let's validate that we are using in mobile app for Android the Android key and not our Firebase key`
> **FMT:** `…and not our Firebase key.`  *(only change is the terminal period)*

**B. ESL grammar repair — aggressive.** This user is a non-native English speaker and the formatter is doing substantial second-language correction:

| ASR | Formatted |
|---|---|
| `deploy a app` | `deploy **an** app` |
| `create merge request` | `create **a** merge request` |
| `in Docker file` | `in **the Dockerfile**` |
| `We using Firebase SDK` | `**We're** using Firebase SDK` |
| `I think we was using three` | `I think we **were** using three` |
| `Why you did not use skill` | `**Why did you not** use skill` |
| `Why DoubleVerify didn't choose…` | `**Why didn't DoubleVerify** choose…` |
| `so image will be small` | `so **the** image will be small` |
| `Please look the login page` | `Please look **at** the login page` |
| `it's not firing like simultaneously queries` | `it's not firing **simultaneous** queries` |
| `If this is not implementation` | `If this is not **implemented**` |
| `Look this input color it's incorrect` | `Look **at** this input color**;** it's incorrect` |

**C. Self-correction and false-start handling — partial but real.**

> **ASR:** `which mean classification project, I mean classification store that we are using SA from.`
> **FMT:** `which **means classification store** that we are using SA from.`
> *The false start "classification project, I mean" is deleted entirely.*

> **ASR:** `What I mean by arrival when you think can be best position or like the area to attack Iran…`
> **FMT:** `What I mean by **"arrival" is** when you think it can be **in the** best position or area to attack Iran, because this is the goal. I need to understand…`
> *Adds the missing copula, quotes the term under discussion, splits the run-on. Note "I mean" is preserved here because it is a legitimate discourse marker, not a restart.*

**D. Numerals.**

> `It's less than 0- it's less than half percent` → `It's less than 0, it's less than **0.5%**`
> `six-team lead promotions` → `**6-team** lead promotions`
> `Gemini two` → `Gemini **2**`

**E. List detection producing real HTML markup.**

> **ASR:** `Let me answer batch one, yes first question, yes, this is accurate, I'm reporting to LAT, the six-team lead promotions is incorrect, let me… I don't remember that I had this goal, it's not relevant I think.`
> **FMT:**
> ```html
> Let me answer batch one:
> <ol>
> <li>Yes, first question, yes, this is accurate, I'm reporting to LAT.</li>
> <li>The 6-team lead promotions is incorrect.</li>
> <li>I don't remember that I had this goal, it's not relevant I think.</li>
> </ol>
> ```

> **ASR:** `Let's rewrite please example about passion, accountability, collaboration, trailblazing and let's take many projects out of them.`
> **FMT:** `Can we find other examples? Let's rewrite please. Example about:` + `<ul><li>Passion</li><li>Accountability</li><li>Collaboration</li><li>Trailblazing</li></ul>` + `Let's take many projects out of them.`

**F. Paragraph breaks.** All whitespace structure is invented by the formatter.

> **ASR:** `…I will raise it better in our meeting. Aside, I also wanted to raise…`
> **FMT:** `…I will raise it better in our meeting.\n\nAside, I also wanted to raise…`

**G. Code and identifier formatting.**

> `by running npm run dev it will trigger the fucking start dev sh`
> → ``by running `npm run dev` it will trigger the `start-dev.sh` ``
>
> `trips new, we have backend function` → `` `trips.new` we have a backend function ``
> `we should not pass local with every rest request` → `` we should not pass `local` with every REST request ``
> `the prompt id` → `the prompt **ID**`

**H. Proper nouns and homophones.**

> `sold to Nelson` → `sold to **Nielsen**`
> `Google places photo` → `Google **Places** photo`
> `only with pinterest` → `only with **Pinterest**`
> `like it's all the floors` → `It's all the **flaws**`
> `resin history` → `**query** history`
> `Let's encry…` → `**Let's Enc**rypt`

**I. Capitalization** of whole-lowercase output, including acronyms:

> **ASR:** `hey guys i wanted to kick off this collaboration on defining the aci vision today…`
> **FMT:** `Hey guys, I wanted to kick off this collaboration on defining the **ACI** vision. Today…`

### 6.3 What it deliberately does *not* do

- **Profanity is preserved verbatim.** (`Fuck.`, `you fucking idiot`, `What the fucking shit?` all pass through unchanged.)
- **Meaning is never summarized.** The length statistics confirm this.
- **Truncated or incomplete utterances stay truncated.**
- **No command interpretation on the dictation path.** `transcriptCommand` is a *mode* label (`ptt` 1652, `popo` 17), and `popo` rows are formatted identically to `ptt` rows.

## 9. Audio pipeline

**Capture** — an `AudioWorkletProcessor` (`renderer/dist/recorderWorklet.js`, 1650 bytes total):

```js

  constructor(e) { super(), this.recording = !1, this.chunkSize = 640,
    this.numInputStreams = e.numberOfInputs, this.renderQuantumSize = 128,
    this.buffer = this.create2DArray(this.numInputStreams, this.chunkSize, Float32Array), …
```

`chunkSize = 640` at 16 kHz = **40 ms frames**.

**Constraints:**

```js
static mediaOptions = { audio: { echoCancellation: !1, noiseSuppression: !1,
                                 autoGainControl: !1, sampleRate: 16000, channelCount: 1 } };
new AudioContext({ sampleRate: 16000, latencyHint: "interactive" })
```

**All DSP disabled. Raw 16 kHz mono.** Their model is trained on unprocessed audio — they explicitly do not want the browser's AEC/NS/AGC touching it.

**Wire format is PCM16 WAV by default.** Each packet is an `Int16Array(640)` (1280 bytes) with `duration: 40`, `encoding: "wav"`.

**Opus is feature-flagged off for dictation** (`use-opus: false`). When enabled it uses WebCodecs `AudioEncoder`, not the wasm:

```js
dp = { codec: "opus", sampleRate: 16000, numberOfChannels: 1, bitrate: 64000 }
```

16 kHz mono, 64 kbps, 20 ms frames. The client keeps **both** buffers in parallel (`wavAudioPackets` and `opusAudioPackets`); the HTTP fallback always uses WAV. There's a runtime bail-out:

```js
c.ZZ.useOpus && d > 2e3 && 0 === p && (s().warn("No opus data received after 2 seconds of wav data, switching to wav"), …)
```

**`opusEncoder.worker.js` is not on the live path.** It is an Emscripten build of opusscript spawned as a Node `worker_threads.Worker` from the main process, used only by the meeting recorder to transcode `mic.pcm` / `system.pcm` into an `.ogg` for upload.

**There is no client-side VAD.** No silero, no webrtcvad, no energy gate. (The 260 "vad" substring hits in the renderer are all i18n — `Archivadas`, `arquivada`, `bara vad du sa`, `dovadă`.) The only local signal analysis is a per-chunk dBFS value shipped alongside each packet purely for the waveform UI, plus an all-zeros silence detector used for the "no audio" diagnostic. **Audio quality is judged server-side** and returned in the partial state as `audio_snr`, `audio_volume`, `mean_alignment_score`, thresholded client-side at SNR < 5 dB, volume < −70 dB, alignment < 0.15.

**Flush cadence:**

```js
if (ct.A.isConnected()) { const e = Et(1/0); ct.A.sendAudioPackets(e) }
else if (dt.MM.isConnected());
else { const e = Math.ceil(1e3 * _.basetenChunkSizeSeconds / i);
       if (u.packets.length - c.ZZ.nextRequestIndex >= e) { … } }
```

With a gRPC stream up, every packet is forwarded immediately. Without one, audio batches into **28-second chunks**.

### 10.1 Service

### 10.3 Partial results are duration-indexed, not diffed

There is **no `isFinal` boolean**. The discriminator is which field is populated: `Response.state` = partial, `Response.result` = final, neither = acknowledgement.

```js
static updateProcessedIndexFromState(e) {
  const t = e.progress; if (!t) return;
  if (!e.rawText?.content && !e.formattedText?.content)
    return void T().info("Skipping transcription state update with empty raw and formatted text");
  const n = this.durationToPacketCount(t.transcriber),
        r = this.durationToPacketCount(t.formatter) == n ? kt.nf.Formatted : kt.nf.RawTranscript,
        i = { status: r, asr_text: e.rawText?.content || "", llm_text: e.formattedText?.content || "", … };
  Ht.ZZ.responses = [i];
  Ht.ZZ.lastProcessedIndex = n
}
static durationToPacketCount(e) {
  const t = this.durationToMillis(e),
        n = Ht.ZZ.useOpus ? Ht.ZZ.opusAudioPackets.packetDuration : Ht.ZZ.wavAudioPackets.packetDuration;
  return Math.ceil(t / n)
}
```

The server reports **how many seconds of audio each stage has consumed**, as a Duration. The client converts to a packet index. If the formatter's duration has caught up to the transcriber's, the state is `Formatted`; otherwise `RawTranscript`. Each state **replaces the entire response** (`Ht.ZZ.responses = [i]`). `lastProcessedIndex` doubles as the retry resume point.

This is a clean design: it sidesteps all the incremental-text-merge and dedup logic that a text-diffing approach forces on you.

### 10.5 The gRPC ↔ HTTP race

The retry ladder has only one rung in this build (`RETRY_PARAMS = [{ encoding: "wav", useHttp: !1 }]`), with probation → blacklist (both aged 1 h). The real resilience is a **parallel race**:

```js
if ("grpc" === this.raceWinner) return void T().info("gRPC already won the race — discarding Baseten HTTP result");
this.raceWinner = "http"; this.lastRaceWinner = "http";
Ht.ZZ.backendServiceUsed = Ht.L_.HttpRace; Ht.ZZ.fallbackLevel = .5;
```

and, notably, a **memory of the last outcome**:

```js
getFeatureFlagData(Bt.TO.GrpcHttpRace).enabled && "grpc" !== this.lastRaceWinner &&
  (T().info("Prior race did not end in gRPC win — starting parallel HTTP fallback immediately", …),
   this.startParallelHttpFallback())
```

If gRPC lost last time, the HTTP fallback fires immediately rather than waiting for a timeout. Every result is checked for staleness against the dictation UUID (`staleFallbackReason` → `changed_uuid` / `dismissed` / `empty_request_uuid`) before being applied.

In all 13 logged sessions, gRPC won (`usedHttp: false`).

### 10.6 Fallback ladder and what happens on total failure

```
fallbackLevel 1: Baseten gRPC (transcribe + align + format)
      ↓ non-"ok" status, throw, or basetenUnavailableThisSession
fallbackLevel 2: _runOpenAIFallback
      ├─ transcribeOpenAI(audio)             → status RawTranscript (NO FORMATTING)
      └─ transcribeOpenAIAudioChunks(opus)   → status RawTranscript
      ↓ both fail
      Error sentinel; metric ("failure", "both_services_failed")
```

Once Baseten fails, `basetenUnavailableThisSession = !0` short-circuits **every subsequent chunk in that session** straight to OpenAI.

At result-assembly time:

```js
if (u.ZZ.isCommandMode || i === C.$Q.Raw) return [n, t];                 // raw
if (n === I.nf.Formatted) return [n, e.llm_text || t];                   // happy path
if (n === I.nf.RawTranscript && u.ZZ.appType !== C.uC.AI) {
  let n;
  if (!["en","english","engb","english_british","enca","english_canadian"].includes(r)) {
    n = await B.AriaWebClient.formatNonEnglish(u.ZZ.appType, t, r, …);
    …
  }
  return n ? (e.llm_text = n, [I.nf.Formatted, n]) : [I.nf.RawTranscript, t]

```

**The fallback is raw ASR.** For English, if the server formatter is unavailable the raw transcript is pasted with only the §8 paste rules applied — the client-side English formatter is dead code. For non-English there is one extra client-initiated call to `/llm/format_non_english`. Apps classified as `appType === "ai"` (Claude, ChatGPT, etc.) are excluded from that fallback.

In the local database this shows as `status = 'raw_transcript'` on 14 of 1,670 rows (0.8%).

### 11.2 Four capture mechanisms

**(a) `GetTextBoxInfo` — focused-element ranged read.** Returns `{contents, beforeText, selectedText, afterText, isEditable}` using `AXSelectedTextRange` / `AXStringForRange` / `AXNumberOfCharacters` to split the field around the caret. Fired at three sites, per their own comment:

> *"The helper fires `updateTextBoxInfo` from three sites: dictation start, focus change (`FocusChangeDetector`), and dictation stop (PTT-stop refresh)."*

Failure modes recorded: `couldNotGetTextBoxInfo`, `accessibilityIsFunctioning === false`.

**(b) `nearestTexts` (`axText`) — bounded AX-tree walk.** A traversal of the focused window collecting text from nearby elements, using `AXChildren`, `AXParent`, `AXRole`, `AXSubrole`, `AXValue`, `AXTitle`, `AXDescription`, `AXWindow`, `AXWebArea`, `AXScrollArea`, `AXVisibleChildren`, `AXTopLevelUIElement`. Bounded, with truncation reasons `["control_limit","depth_limit","node_limit","provider_error","text_limit"]`. Sets `AXManualAccessibility` to force Electron/Chromium targets to expose their tree.

**(c) `markerRange` — private WebKit `AXTextMarkerRange`, no traversal.** Using `AXTextMarkerRef`, `AXTextMarkerRangeRef`, `AXStartTextMarker`, `AXSelectedTextMarkerRange`, `AXSharedCharacterRange`, `AXAttributedStringForTextMarkerRange`. This yields **the entire logical document of a web view in a single call** — dramatically cheaper than tree-walking. Their fallback message: *"No markerRange text — the focused app did not expose the AXTextMarkerRange APIs."*

Ordering, per their comment:

> *"the helper builds nearestText (nearestTexts) then captures the focused element's markerRange document text, in that order, before sending `AppContextUpdate`."*

**(d) OCR + screenshot.** `Context.screenshot` and `DynamicVocabulary.screen_content_ocr` in the proto, plus `extractProperNounsFromScreenCapture(image)` → `POST /llm/ocr`. Used when AX yields nothing usable. In this user's config, `shouldOCRScreenCapture: false`, so `ocr_context` is empty.

### 11.3 Two consumers, two truncation budgets

From their own comments:

> *"The primary proper-noun extractor (`/llm/extract_asr_words` → gpt-4o-mini) trims its input before the model sees it: aria-web's `api_service.extract_asr_words` keeps the first 2,500 + last 2,500 chars once the text passes 5,000 (head+tail, middle dropped)."*

So `axText` goes two places: **head+tail-capped at 5,000 chars to GPT-4o-mini** for proper-noun mining, and in full to local static name-list and variable miners. The extraction races the dictation — a `raceLost` badge means *"Extraction finished after the dictation had already finalized — its vocabulary arrived too late to influence the transcript."*

## 12. The correction-learning loop

This is the most sophisticated part of the product and the hardest to replicate.

### 12.1 Post-paste observation, 60 seconds

After pasting, the helper keeps watching the target field:

- **Insertion verification** — re-reads the focused element and records `focusedElementContents` with verdicts `verified` / `verified_before_after` / `not_found` / `skipped`.
- **Edit observation** — **26 distinct `contentObservationEndReason` values**: `observation_window_elapsed`, `textbox_emptied`, `next_paste_started`, `edit_distance_exceeded`, `transcript_region_removed`, `message_sent`, `app_termination`, and 19 more. Plus a normalized Levenshtein `editDistance`.
- **Keystroke trace** — a **global key tap**. Two mitigations documented in their own source:
  - *"Category only; the helper never forwards keycodes or characters"* — for the terminal-gesture disambiguator (`return`, `cmd_enter`, `backspace`, `delete_word`, `select_all_delete`, `cmd_z`, `cmd_x`, `esc`).
  - *"Recorded only with the internal `shouldSaveAxText` toggle on; local-only, never uploaded."* But when that toggle **is** on, they capture *"glyphs for special keys (⏎ ⌫ ⎋ …), **layout-resolved characters** otherwise."*
  - *"The tap/hook is global, so a burst is not necessarily this dictation's: `out` = the observed textbox had lost focus."* Keys typed into other windows are captured and filtered after the fact.

### 12.2 The edit vector

`History.userEditMetaData` stores a per-word flag string:

```json
{"word_edits":"MMMMMMMMMMM...","punctuation_edits":"ZMZZZZMMZZZZ..."}
```

One character per word, `M`/`Z` marking which words and which punctuation marks the user changed after paste. Combined with `editDistanceToDictated` (*"normalized Levenshtein distance from the last trusted live-region read"*) and `numWordsCorrected`, this is a dense, per-token training signal collected without ever asking the user anything.

### 12.3 Dictionary auto-learn, LLM-gated

```js
const l = o < pe;
…
l && e && (s().info("Transcription sensibility below threshold, running auto-polish",
                    { score: o, threshold: pe }),
           await (0, M.w3)(e))
```

If the server's "does this text make sense?" score falls below 0.4, they run auto-polish on it unprompted. `/llm/check_sensibility` is a dedicated endpoint for this.

Every polish failure mode ends in *keep the user's original text*: `PolishTimeout`, `PolishEmptyResponse`, `PolishTextFailed`, `PolishMaxWords` (1000 words), `PolishCancelled`, `PolishTextNoChanges`, `PolishTextNoSelection`, `PolishTextNotEditable`, `PolishTextboxDetectionFailed`, `PolishDisabledDuringDictation`.

Polish timing constants: 60 s operation window, 40 s undo-detection window, 1200 ms wait for paste outcome, 750 ms "no changes" notification delay.

**Five independent signals that this is a network pipeline:**

1. `clientNetworkLatency` exists as a first-class database column, populated on every row, with a **47 ms floor**. That's an RTT, not a compute floor.
2. Median e2e of 930 ms with a hard floor even on near-zero-length clips. Local inference on Apple Silicon would have a floor near zero on empty audio.
3. e2e scales only **1.6×** from 2 s to 30 s of speech (676 → 1742 ms). Sub-linear scaling is the signature of a batched server-side encoder behind a fixed network cost, not on-device streaming decode.
4. `e2eLatency − clientNetworkLatency` ≈ 716 ms of server compute for ASR + formatting.
5. `formattedText` and `serverFinalizedText` are separate columns that disagree in 93% of rows where both exist — a purely local pipeline would have no such split.

**Where their time goes, at the median:** ~214 ms network, ~235 ms GPU queue, ~200 ms ASR compute, ~100 ms LLM format, ~15 ms paste. A quarter of their server time is queue contention, not inference.

### 16.7 Auth

**Supabase GoTrue JWT pair**, `flowType: "implicit"`, `storageKey: "supabase.auth.token"`, `autoRefreshToken: true`.

Device-code sign-in flow:

1. Client mints `crypto.randomUUID()` as the device code.
2. Opens `https://wisprflow.ai/login?device_code=…&auto_signin=true&skip_default_trial=true&grant_weekly_bonus=true` in the system browser.
3. **Primary channel is SSE**: `GET /device/stream?device_code=…` with `Accept: text/event-stream`, parsing `data: {status:"complete", access_token, refresh_token, …}`.
4. **Fallback poll**: `GET /device/poll?device_code=…`, exponential backoff `min(2000 · 2^(n−1), 30000)`.

## 20. Security and privacy observations

Recorded factually. Several of these are ordinary consequences of shipping a desktop client; a couple are not.

1. **A static, shared Baseten API key ships in the client.** It lives as a plaintext constant in `main/index.js` and is sent as `baseten-authorization: Api-Key …` on every dictation. It is workspace-level, not per-user — every installed copy shares it, and anyone who unpacks the asar can invoke Wispr's production Baseten deployment directly. *(Key value deliberately not reproduced in this document.)*

2. **The Supabase anon JWT is hard-coded** with `"role":"anon"` and an expiry in 2034. Normal for Supabase clients, but a 10-year expiry means no rotation path short of a client release.

3. **`net.log` is an unrotated Chromium NetLog** — 9.5 MB on this machine, dating to Dec 2025, mode `0600`, containing complete request headers including live user JWTs and the Baseten key in plaintext. It is never rotated or deleted and would be swept up by any "send us your logs" support flow.

4. **`flow.sqlite` is unencrypted** and retains per dictation: `audio` (blob), `screenshot` (blob), `opusChunks`, `axText`, `axHTML`, and the full text of surrounding fields. Their own dev tooling says so verbatim: *"Reads the local, unencrypted flow.sqlite…"*.

5. **A global keystroke tap runs for 60 s after every paste.** Categories only by default, but full layout-resolved characters when the internal `shouldSaveAxText` toggle is enabled. The tap is global, so keystrokes destined for other applications are captured and then filtered out after the fact.

6. **`axHTML` is helper-generated HTML embedding unescaped text scraped from other applications** — a stored-XSS primitive in any viewer that doesn't strip it. Their own dev tool comments catch this: *"The Swift helper does not escape captured screen text, so strip any `<script>` from the axHTML."*

7. **Broad context exfiltration is on by default.** With `useAxContext: true`, the focused window's accessibility tree, window title, tagged IDE filenames, and browser tab contents are POSTed to `/llm/extract_asr_words`. In this install, a window title reading `"Generate documentation — aci-vision"` and Chrome tab scans went to the server.

8. **`edge-proxy` steers microphone audio via a plaintext file.** A hostname fetched over HTTPS from `inference-info.wisprflow.com/dictation_url.txt` redirects all dictation traffic. It *is* allowlist-validated client-side against three hosts, which is the correct mitigation — but a compromise of that file plus one allowlisted host would reroute every user's audio.

9. **Boot-time trust-store widening.** The log shows *"Evaluating 89 System certs" → "Injecting 69 system root certs into Node.js" → "System trust store applied {appliedCount: 174, preWidenCount: 145, addedCount: 29}"*. Adding 29 trust anchors to Node is a meaningful attack-surface expansion. There is a kill switch (`desktop-disable-system-trust-store`, currently false).

10. **Unminified dev tooling ships in the release bundle** — three `.mjs` files whose comments expose internal service names, source paths, and a loopback dashboard that renders unescaped cross-application screen text.

11. **Facebook attribution cookies** (`fbp`, `fbc`) are propagated from the web signup flow into the desktop session payload.

## 21. Implications for Whisperer

### 21.1 Where their architecture beats ours

**Context biasing is their real moat, not the model.** Feeding the ASR the user's dictionary, the AX-scraped screen, and the text around the caret is what turns `Glyn` into `Glean` and `resin history` into `query history`. None of that requires a bigger model. Whisperer already has a `Dictionary/` module and a `LanguageRouter`; the gap is that we don't assemble screen context or caret-adjacent text into a recognition prompt. whisper.cpp accepts an `initial_prompt` — that's an unexploited lever.

**The correction-learning loop is the highest-leverage feature we don't have.** Watching the target textbox after paste, diffing it, and auto-promoting `observedSource → phrase` into the dictionary produced nine high-value entries for this user, two of them used 87 and 105 times. It requires no user effort. Whisperer has the injection path and the history store; the missing piece is the post-paste observation window.

**Duration-indexed partial results are cleaner than text diffing.** Their server reports how many seconds of audio each stage consumed; the client converts to a packet index and replaces the whole response. Our live preview does append-only text merging with word dedup and a `previewPassID` for ordering — which works, but the duration-index approach sidesteps the entire class of merge bugs. Worth considering if we ever revisit `LiveTranscriptionCard`.

**The `raw_transcript` vs `formatted` status split as a first-class state.** They paste raw ASR immediately, then upgrade to formatted. We could apply the same idea locally: inject the whisper.cpp output, then let `PolishEditor` upgrade it in place.

**Trailing-period suppression in messaging apps.** Small, but it's exactly the kind of detail that makes dictation feel native. Their implementation (§8.2) is ~15 lines and app-aware.

### 21.2 Where our architecture beats theirs

**Latency floor.** Their p5 is 415 ms and their network overhead alone is 169–294 ms, with a further 235 ms median of GPU queue wait. On-device Metal inference has no RTT and no queue. Our floor is bounded by encode time, not by geography — and their own numbers show 45% of their latency is not compute.

**Offline.** They produce no text without a network. That is a categorical capability difference, not a quality difference.

**Privacy as an architectural property, not a policy.** Their raw microphone audio, screen contents, window titles, and caret-adjacent text leave the machine on every dictation. Ours does not leave the process. This is the single clearest differentiator and it is structural — they cannot match it without rebuilding.

**App Store distribution.** Their entitlements (`allow-unsigned-executable-memory`, `disable-library-validation`) and their global keystroke tap make sandboxed distribution impossible. They ship Developer ID only. We are targeting an App Store channel they have structurally forfeited.

**Cost.** Their per-dictation cost is an ASR ensemble call plus one to three LLM calls across four vendors. Ours is amortized silicon.

### 21.3 Specific things worth stealing

1. **Feed `initial_prompt` with dictionary + AX context.** Highest value-per-line-of-code item in this document.
2. **Post-paste observation window** with an edit-distance threshold and an auto-learned dictionary carrying `observedSource` provenance.
3. **The cleanup-level ladder** (`none/light/medium/high`) with worked before/after examples in the UI. Their four-example string (§6.4) is a better product spec than most PRDs.
4. **Per-app style profiles** keyed on bundle ID (work / email / personal / other) with per-profile cleanup strength.
5. **Trailing-period suppression** in messaging contexts, gated on surrounding punctuation.
6. **Snippet triggers that bypass punctuation** when the whole utterance is a trigger phrase.
7. **A `formattingDivergenceScore`** stored per dictation — cheap telemetry that tells you when your formatter is being too aggressive.
8. **A sensibility gate** — if the output scores below a threshold, run a second pass. Ours could be a local heuristic rather than a network call.

### 21.4 Things to deliberately not copy

- The global keystroke tap. Beyond being an App Store non-starter, it is the single most invasive thing in their client.
- Shipping dev tooling and static vendor API keys in the release bundle.
- An unencrypted local database holding raw audio and screenshots.
- Making the client a policy-free terminal. Their zero-client-configuration approach is right *for a cloud product*; for an on-device product the model choice is the user's, and hiding it would be user-hostile.

### 21.5 The one uncertainty worth resolving

We know their backend *can* return a multi-engine N-best list with per-word alignments. We do not know, from static analysis alone, whether a given request is served by one engine or a fusion — the client discards `candidate_beams`, and `use-ensemble-model` is `false` for this user. If that question matters to a product decision, it would need traffic capture, which was outside the scope of this analysis.

## Appendix B — Method and limits

Six parallel analysis passes were run over the artifacts above: database and migrations; streaming ASR path and transport; on-device inference verification via `otool`/`nm`/`strings`/`codesign`; configuration, feature flags and runtime logs; the polish and formatting pipeline; and the network/protobuf surface plus accessibility tooling.

**Everything in this document is from static analysis of files already on this machine.** No network requests were issued to Wispr infrastructure, no traffic was intercepted, no credentials were used, and no attempt was made to access their services.

**Known limits:**

- Which single ASR engine served any given request is not determinable statically — the client discards `candidate_beams`.
- What `MIXTURE` fuses, and how, is entirely server-side.
- The main `FORMAT` step's prompt does not exist in the client; it is in the OpenPipe fine-tune's weights and/or server-side. The `auto_cleanup_level` descriptions and worked examples are the best available proxy for its specification.
- Whether Soniox is on the dictation path is unresolved. The `soniox_5xx` error bucket exists only in the cloud-sync/upload classifier; no Soniox endpoint or credential is in the bundle.
- Where the `SLACK_TAGGING` and `EMAIL_SIGNATURE` pipeline steps get added is unknown — they exist in the enum but no client code pushes them.
- Payload shapes for `/llm/classify_intent`, `/llm/command_mode`, `/llm/command_mode_route`, and `/llm/voice_profile` were not traced.
- Findings reflect one user's install, one A/B assignment (`qwen`), and one flag snapshot. Another user may be routed entirely differently.

# Feature Spec Template

Use this format for every finding in Phase 2 dimension files and in the final `FEATURE-SPECS.md`.
Each finding is one `###` block. Copy the template exactly — don't abbreviate fields.

---

```markdown
### <Feature name>  ·  AHEAD | GAP | BEHIND  ·  Impact: H | M | L  ·  Effort: S | M | L
<!-- AHEAD = they beat us on this  |  GAP = we have nothing equivalent  |  BEHIND = we're stronger -->
<!-- Impact: H = changes retention / conversion / core UX  M = meaningful improvement  L = nice-to-have -->
<!-- Effort: S = < 1 sprint  M = 1-2 sprints  L = > 2 sprints or risky rearchitecture -->

**What it is**
One paragraph. Describe the feature purely from the user's perspective — what they see, feel, or save. No implementation details here.

**Evidence**
- E-{nnn} · `SIGNAL:` …  `SOURCE:` path:line / URL  `FACT:` …
- E-{nnn} · `SIGNAL:` …  `SOURCE:` …  `FACT:` …
- Validation level: `preliminary` | `candidate` | **`validated`** (≥2 independent — required for ADOPT)
- `Inference:` (if any non-literal deduction — mark clearly)

**How they built it**
Mechanism description. Architecture, data flow, key technology choices. Be concrete. If uncertain, prefix with `Inference:`.

**What we do today**
Our behavior on this axis. File paths (use codegraph to confirm before writing). If we have nothing: "We have no equivalent."

**Why theirs wins** (only for AHEAD and GAP findings)
The concrete axis: milliseconds saved, taps eliminated, error class avoided, clarity gained, privacy story stronger, etc. Quantify where evidence supports it. Avoid vague claims like "better UX".

**Why ours wins** (only for BEHIND findings)
Same — concrete and evidenced.

**Verdict**
ADOPT — adapt this directly; the mechanism is clean and fits our architecture.
ADAPT — the idea is right but their mechanism conflicts with our constraints; describe the clean-room reinterpretation.
REJECT — the idea is appealing but conflicts with CLAUDE.md Critical Rules, App Store framing, or our product philosophy; state which rule.
WATCH — not yet worth building but worth tracking; set a condition for when it becomes ADOPT.

**Adaptation sketch** (for ADOPT and ADAPT)
Which Whisperer files change. What the new flow looks like. Any new state or persistence. One paragraph max.

**Risks**
Check against:
- CLAUDE.md Critical Rules: 2.4.5 (no CGEventTap/IOHIDManager/global keyDown), MainActor isolation, SafeLock over actors, await stopAsync not sync stop, offline claim accuracy
- App Store framing: no "accessibility" / "assistive" framing, no "Grant [Permission]" button labels, no disability framing
- Architecture: Metal contention, ModelPool warm check (binary not language), no second whisper context
- Privacy: no competitor data leaking into our source; docs/competitive/ must stay gitignored
```

---

## Severity tags (add to `###` line when relevant)

- `🔴 blocks-us` — their implementation is feasible for us AND users are actively choosing them over us because of it
- `🟡 erodes-us` — we're losing ground slowly; no single-moment churn but compounds over months
- `🟢 strategic` — not urgent but defines where the product category is going in 12-24 months
- `⚪ informational` — recorded for completeness; no action needed
